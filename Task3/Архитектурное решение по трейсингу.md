### 1. Анализ системы и идентификация "узких мест"

Проанализировав C4-диаграмму и описание статусов заказа, я выделил ключевые точки, где заказ может "сломаться" или зависнуть. Именно эти взаимодействия должны быть покрыты трейсингом.

**Проблемные зоны (границы трейсов):**

1.  **Создание заказа (Frontend -> Shop API):** Может ли фронтенд отправить некорректные данные? Не падает ли API при сохранении?
2.  **Расчет стоимости (Shop API -> MES API (async)):** Это самое "слепое" место. Заказ ушел из Shop API в очередь, но дошел ли до MES? Посчиталась ли цена? Ответ от MES пришел ли обратно в CRM/Shop?
3.  **Подтверждение заказа (CRM -> MES API (async)):** Продавец подтвердил заказ в CRM. Ушло ли сообщение в MES? Началось ли производство?
4.  **Работа оператора (MES -> MES API):** Оператор меняет статус (STARTED, COMPLETED, SHIPPED). Сохраняется ли это в БД? Отправляется ли уведомление в CRM?
5.  **Взаимодействие с API (в целом):** Любой вызов API может быть медленным или ошибочным из-за проблем с БД или внутренней логикой.

### 2. Список данных для трейсинга

Каждый спан (единица работы) должен содержать следующие данные для возможности трассировки заказа:

| Поле | Описание | Пример |
| :--- | :--- | :--- |
| **Trace ID** | Уникальный идентификатор всего запроса/процесса | `order-12345-abc` |
| **Span ID** | Уникальный идентификатор конкретной операции | `span-67890-def` |
| **Parent Span ID** | Ссылка на родительскую операцию | `span-12345-abc` |
| **Service Name** | Имя сервиса | `shop-api`, `mes-api`, `crm-api` |
| **Operation Name** | Название операции | `POST /orders`, `calculate_price`, `update_status` |
| **Start/End Timestamp** | Время начала и окончания операции | `2024-01-15T10:00:00Z` |
| **Duration** | Длительность операции | 150ms |
| **Status** | Успех или ошибка | `OK`, `ERROR` |
| **Business Attributes** | Бизнес-атрибуты для поиска | `order_id=12345`, `user_id=678`, `status=SUBMITTED` |
| **Error Details** | Детали ошибки (если есть) | `stack trace`, `error message` |

### 3. Мотивация (Почему это нужно бизнесу?)

Уважаемые коллеги,

Мы внедрили мониторинг и теперь видим, что система в целом работает или не работает. Но мы до сих пор не знаем, **почему** конкретный заказ клиента Иванова завис на стадии "Расчет стоимости" уже три часа. Мы тратим часы на копание в логах разных сервисов (Shop API, CRM, MES, RabbitMQ), пытаясь восстановить цепочку событий. Это неэффективно и демотивирует команду.

**Что нам даст трейсинг:**

1.  **Скорость расследования инцидентов (техническая метрика):** Вместо часов поиска по логам, мы получим единую "киноленту" жизни заказа. Время диагностики проблемы (MTTR) сократится с часов до минут.
2.  **Улучшение взаимодействия между командами (бизнес-метрика):** Мы перестанем перекладывать ответственность ("Это баг в MES!", "Нет, это CRM криво отправила данные"). Трейсинг покажет объективную картину.
3.  **Повышение прозрачности для поддержки (бизнес-метрика):** Продакт-менеджер или тимлид смогут сами найти заказ по номеру и увидеть, на каком этапе он находится и не было ли ошибок. Это повысит качество коммуникации с бизнесом.
4.  **Оптимизация производительности (техническая метрика):** Мы увидим, какой именно запрос к БД или вызов внешнего сервиса тормозит весь процесс.
5.  **Улучшение качества данных (бизнес-метрика):** Мы сможем отследить, не теряются ли сообщения в RabbitMQ, и гарантировать, что каждый заказ пройдет полный цикл.

Внедрение трейсинга — это **инструмент для повышения доверия к системе**. Когда бизнес и клиенты не сомневаются, что их заказ не потеряется, а инженеры могут быстро найти и исправить любую проблему.

### 4. Предлагаемое решение

Для реализации трейсинга я предлагаю использовать стек **OpenTelemetry** (сбор и генерация трейсов) + **Jaeger** (хранение и визуализация). Это открытый стандарт, который поддерживается и Java, и C#, и не привязывает нас к конкретному вендору.

**Компоненты решения:**

1.  **OpenTelemetry SDK:** Встраивается в каждое приложение (Shop API, CRM API, MES API, а также фронтенд-приложения) для автоматического и ручного создания спанов.
2.  **OpenTelemetry Collector:** Принимает трейсы от приложений, агрегирует, добавляет метаданные и отправляет в хранилище.
3.  **Jaeger:** Хранит и индексирует трейсы, предоставляет UI для поиска и визуализации.
4.  **RabbitMQ Tracing Plugin:** Позволяет отслеживать прохождение сообщений через очередь, связывая производителя и потребителя.

**Необходимые доработки:**

*   **Java-сервисы (Shop, CRM):** Добавить зависимость `opentelemetry-javaagent` и настроить автоматическое инструментирование Spring Boot. Добавить ручное создание спанов для бизнес-событий (изменение статуса заказа).
*   **C#-сервис (MES):** Добавить пакет `OpenTelemetry.Extensions.Hosting` и настроить экспорт трейсов.
*   **Vue/React (Фронтенд):** Добавить `@opentelemetry/instrumentation-document-load` и `@opentelemetry/exporter-trace-otlp-http` для отправки трейсов с клиента.
*   **RabbitMQ:** Включить плагин `rabbitmq_tracing` или настроить плагин `opentelemetry-erlang` для проброса контекста трейсинга через заголовки сообщений.
*   **Передача контекста:** При отправке сообщения в RabbitMQ, MES и CRM API должны пробрасывать заголовки трейсинга (W3C Trace Context), чтобы получатель мог продолжить ту же трассу.

### 5. Компромиссы

1.  **Производительность:** Внедрение трейсинга добавляет небольшую задержку (обычно < 5%) на каждый запрос из-за генерации и экспорта спанов. Это приемлемый компромисс за получаемую наблюдаемость. Мы можем использовать адаптивную выборку (sampling) — сохранять 100% трейсов для ошибок и, например, 10% для успешных запросов.
2.  **Сложность отладки асинхронных сценариев:** Проброс контекста трейсинга через RabbitMQ потребует доработки кода в трех сервисах (Shop, CRM, MES). Это не очень сложно, но требует времени и внимания разработчиков.
3.  **Хранилище:** Хранение всех трейсов может быть дорогим. Jaeger позволяет настроить политики хранения (например, хранить "горячие" данные 7 дней, "холодные" — в S3).
4.  **C# и Java:** OpenTelemetry имеет зрелую поддержку для обоих языков, но настройка может отличаться. Потребуется координация между Java- и C#-разработчиками.
5.  **Устаревшие участки кода:** Если в каком-то сервисе есть плохо структурированный код, ручное добавление спанов может быть нетривиальной задачей.

### 6. Аспекты безопасности

1.  **Аутентификация и авторизация:** Доступ к Jaeger UI будет защищен. Мы интегрируем его с корпоративным SSO (например, Keycloak или Яндекс ID). Права доступа:
    *   **Только чтение:** Разработчики, QA, тимлид, продакт-менеджер (могут только искать и смотреть трейсы).
    *   **Администратор:** DevOps-инженер (может менять настройки, политики хранения).
2.  **Маскирование данных:** OpenTelemetry Collector может быть настроен на фильтрацию или маскирование чувствительных данных (например, номера телефонов, адреса) до того, как они попадут в хранилище.
3.  **Безопасность передачи:** Все данные трейсинга будут передаваться по зашифрованным каналам (gRPC с TLS) между агентами, коллектором и хранилищем.
4.  **Аудит:** Будет настроено логирование доступа к Jaeger UI для отслеживания, кто и когда искал трейсы (важно для GDPR и compliance).

### 7. Дополнительное задание: Автоматический мониторинг процесса заказа на основе трейсинга

**Идея:** Использовать данные трейсинга не только для постфактум-анализа, но и для проактивного мониторинга бизнес-процессов.

**Как это будет работать:**

1.  **Генерация бизнес-метрик из трейсов:**
    *   При изменении статуса заказа (например, с `SUBMITTED` на `PRICE_CALCULATED`) мы создаем span с атрибутами `order_id` и `new_status`.
    *   OpenTelemetry Collector (или отдельный компонент, например, **Prometheus-span-metrics**) будет агрегировать эти спаны и превращать их в метрики для Prometheus.
    *   Мы получим метрики, аналогичные тем, что предлагались в задании 2, но теперь они будут построены на реальных данных прохождения заказов.

2.  **Бизнес-алерты на основе трейсов:**
    *   **Алерт "Зависший заказ":** Правило в Prometheus: если заказ находится в статусе `SUBMITTED` дольше 30 минут (на основе данных из трейса), но не перешел в `PRICE_CALCULATED` — создать алерт.
    *   **Алерт "Потеря сообщения":** Если мы видим span отправки в RabbitMQ от CRM API, но не видим соответствующего span получения в MES API в течение, скажем, 5 минут — срабатывает алерт. Это позволит ловить потерю сообщений на ранней стадии.
    *   **Алерт "Замедление процесса":** Если p95 времени между статусами `MANUFACTURING_STARTED` и `MANUFACTURING_COMPLETED` превысило 2 часа (норма — 1 час) — алерт для руководителя производства.

3.  **Дашборд для бизнеса в Grafana:**
    *   Создадим дашборд, который в реальном времени показывает "тепловую карту" заказов. Продакт-менеджер сможет увидеть, сколько заказов "застряло" на каждом этапе.
    *   Возможность "провалиться" из метрики в конкретный трейс в Jaeger одним кликом.
